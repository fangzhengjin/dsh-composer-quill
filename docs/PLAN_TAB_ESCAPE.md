# 方案：按下一个键仍能离开输入框（保持 Tab 采纳）

> **状态：已实施，键位在 0.31.47 更正为 `Ctrl+Tab`。** 状态行不显示，只在设置页写明。
>
> `Alt+Tab` 在 Windows 上由系统窗口管理器截获，到不了页面；夹具里看到的 Trusted 按键来自 Playwright 的 CDP 注入，绕过了操作系统，不能作为证据。`Ctrl+Tab` 与 `Shift+Tab` 同样不采纳，前者向前、后者向后。

## 0. 现状

| 场景 | 现在发生什么 |
|---|---|
| 有建议，光标在末尾 | `Tab` 被采纳占用（`preventDefault` + `stopPropagation`） |
| 有建议，光标在句中 | `Tab` 也采纳：整段替换成「原草稿 + 尾巴」（0.31.23 起） |
| 无建议 | `Tab` 交还宿主，正常走焦点 |
| 按 `Esc` 再 `Tab` | 建议消失，`Tab` 走焦点——这条已在 0.31.29 用**真实按键**验过 |

问题不在「Tab 被占用」本身（那是产品选择），而在**没有任何组合键能在建议显示时离开输入框**。屏幕阅读器 / 纯键盘用户唯一的办法是先 Esc，等于为了换焦点先放弃建议。

## 1. 方案：`Alt + Tab`（或 `Shift + Tab` 已占用时不适用）

建议显示时：

| 按键 | 行为 |
|---|---|
| `Tab` | 采纳（现状不变） |
| **`Alt + Tab`** | **不采纳**，交还宿主走焦点 |
| `Shift + Tab` | 交还宿主（0.31.21 起就是这样） |
| `Esc` | 关闭建议，之后 Tab 正常 |

实现只需在采纳分支前加一条判定：

```js
if (event.key === 'Tab' && !altKey && !shiftKey && ...) { accept() }
```

即把现有条件从「没有 shift/ctrl/meta」扩展为「也没有 alt」。`Alt+Tab` 在个别系统上是切窗口（Windows）——但**浏览器里 contenteditable 的 alt+Tab 通常仍会派发 keydown**，且即便被系统截走，Ctrl+Tab 也可作为备选。

## 2. 为什么不让出 Tab、改用别的键采纳

这是另一条路（把采纳挪到 `→` 或双击建议行）。不推荐的原因：

- 现在的可发现性来自「Tab = 采纳」这条通用约定，换键意味着设置说明、README、状态行提示全部要改
- `→/←` 已经被「下一句」的多候选切换占用
- 双击建议行对键盘用户没有帮助

`Alt+Tab` 的代价是「多记一个组合键」，收益是「不需要放弃建议就能换焦点」。比起挪走 Tab，改动面和认知负担都更小。

## 3. 需要一并处理的细节

1. **状态行提示**：现在是 `Tab 采纳 · Esc 关闭 · Ctrl+Shift+Space 手动`，加一项 `Alt+Tab 切焦点` 会让这行变长。建议只在**设置页的帮助文字**里写，状态行保持三项（那里已经够挤）。
2. **`aria-keyshortcuts`**：建议行按钮可加 `aria-keyshortcuts="Tab"`，让读屏器报出可用快捷键。
3. **文档**：README 的键盘说明现在写的是「先按 Esc 关掉建议，Tab 就交还给宿主」，要改成「按 Alt+Tab 直接换焦点；Esc 仍是关闭」。

## 4. 测试

| 类型 | 断言 |
|---|---|
| 场景 | 建议可见时按 `Alt+Tab`：草稿不变、焦点离开输入框（用真实按键，和 S35 一样用 `page.keyboard`） |
| 场景 | 建议可见时按 `Tab`：仍然采纳（S1 已有，防回归） |
| 场景 | `Alt+Tab` 之后再按 `Tab`：焦点继续前进，不会把建议塞进草稿 |
| 单测 | 纯判定函数 `isAcceptKey({ key, shiftKey, altKey, ctrlKey, metaKey })`，与 `statusChipKind` 同层，锁住组合条件 |

## 5. 需要你确认

1. **键位**：`Alt+Tab`（我倾向）还是 `Ctrl+Tab`？后者在浏览器里更常被标签页占用，但 contenteditable 里多半能拦到。
2. **要不要在状态行显示**：我建议不显示（那行已经三项），只在设置页说明。
3. **`Alt+Tab` 被系统截走时**（部分 Windows 环境），是否需要 `Ctrl+Tab` 作为第二备选——两条都留会让「哪些键不采纳」变得难讲，我倾向只留一条。
